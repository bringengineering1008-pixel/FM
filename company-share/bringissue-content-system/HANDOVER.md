# 브링이슈 콘텐츠 운영 인수인계서

최종 정리일: 2026-09-01  
보관 위치: `company-share/bringissue-content-system/`  
작업 브랜치: `codex/bringissue-content-archive`

## 1. 이 문서의 목적

이 폴더는 브링이슈 네이버 블로그의 기획, 원고, 시각자료, 발행 검수, 성과 기록과 텔레그램 알림 도구를 회사 저장소 안에서 독립적으로 관리하기 위한 공간이다.

다른 회사 프로젝트와 섞이지 않도록 이 폴더 밖의 파일은 수정하지 않는다. 기본 브랜치에 병합하기 전에는 회사 담당자가 변경 범위와 비밀정보 포함 여부를 다시 확인한다.

## 2. 운영 대상과 계정 구분

- 블로그: `https://blog.naver.com/bringissue`
- 외부 Chrome 전용 계정: `rancemo858`

### Codex 인앱 브라우저

- 네이버 계정: `dpvld858`

1. 네이버 화면에서 현재 로그인 계정을 먼저 확인한다.
2. 요청 계정과 다르면 글 수정이나 발행처럼 상태가 바뀌는 작업을 하지 않는다.
3. 사용자의 요청 없이 계정을 전환하거나 새로 로그인하지 않는다.
4. 쿠키, 비밀번호, 인증 코드와 세션 파일은 저장소에 넣지 않는다.

## 5. 콘텐츠 방향

기본 운영축은 다음 세 가지다.

1. 돈·보험·연금 등 장기 검색형 정보
2. 화제가 된 영상·인물·작품을 실제 장면과 확인 자료로 해설하는 유입형 콘텐츠
3. 여행, 보안, 디지털 복구 등 40대 이상 독자가 저장하고 다시 찾을 생활 문제 해결형 콘텐츠

최근 계획이나 비율은 고정 규칙으로 취급하지 않는다. 새 주제 선정 전에 반드시 다음 자료를 읽고 실제 최근 성과와 중복 여부를 확인한다.

1. `blog/automation/performance-ledger.csv`
2. `blog/automation/topic-cooldown.csv`
3. `blog/automation/alerts.md`
4. `blog/automation/backlog.md`가 존재하면 함께 확인

## 6. 한 편 제작 절차

### 1단계: 주제와 역할 결정

- 한 독자
- 한 문제
- 한 약속
- 한 개의 주 CTA

글의 역할은 유입, 검토, 증거, 신뢰 중 하나를 주역할로 선택한다. 보조역할은 최대 하나만 둔다.

### 2단계: 최신 사실 확인

정책, 법률, 가격, 요금, 안전, 제품 사양, 일정과 지원사업은 발행 당일 공식 사이트에서 다시 확인한다.

- 공식 페이지의 실제 내용을 열어 확인한다.
- `source_date`와 `verified_on`을 브리프에 기록한다.
- 링크 제목만 보고 내용을 추정하지 않는다.
- 근거 없는 숫자, 기간, 효과와 순위를 만들지 않는다.

### 3단계: 이미지 구성

- 실제 공식 사이트·앱 화면과 권리가 확인된 실자료를 우선한다.
- 독자가 실제로 무엇을 눌러야 하는지 알 수 있도록 필요한 단계만큼 캡처한다. 이미지 수를 임의로 5장이나 10장으로 고정하지 않는다.
- 화면이 잘리거나 글자가 읽히지 않는 캡처는 사용하지 않는다.
- 공식 화면은 AI 이미지나 Google Flow 디자인으로 대체하지 않는다.
- AI 이미지는 설명용 디자인에만 사용하며 실제 화면이나 현장 증거처럼 표현하지 않는다.
- 현장사례에는 AI 이미지를 사용하지 않는다.
- 얼굴, 전화번호, 계좌, 주소, 호실, 차량번호, 계약서 식별정보는 공개 전에 가린다.
- 모든 로컬 이미지는 실제로 열어 보고, 이미지 원장에 역할·보이는 사실·가림 여부를 기록한다.

### 4단계: 원고 작성

- 회사 인사말보다 독자가 겪는 실제 상황으로 시작한다.
- 제목이 약속한 질문에 본문이 명확하게 답해야 한다.
- 모바일 기준 한 문단은 1~3개의 짧은 문장으로 구성한다.
- 한 줄이 지나치게 길어지지 않도록 자연스러운 의미 단위로 끊는다.
- 번호 소제목은 `1. 제목` 뒤에 빈 문단을 두고 설명을 시작한다.
- 서로 이어지는 문장은 묶되 대상·상황·판단·행동이 바뀌면 빈 문단 하나를 둔다.
- 의미 없는 점 목록, 반복 체크박스와 기계적인 AI 문구를 쓰지 않는다.
- 인용구는 핵심 판단이나 전환에만 사용한다.
- 문자로 만든 구분선 대신 네이버 편집기의 실제 구분선 컴포넌트를 사용한다.
- 문단 본문은 가운데 정렬을 기본으로 하되 번호 목록·비교표·절차처럼 정렬이 중요한 블록은 읽기 좋은 형태로 별도 구성한다.
- 표가 필요하면 이미지로 흉내 내지 말고 네이버 편집기의 표 기능을 사용한다.
- 네이버 스티커는 문맥상 감정이나 전환을 돕는 위치에 사용한다. 개수를 고정하지 않지만 정보보다 스티커가 더 두드러지게 만들지 않는다.
- 첫 단에는 글의 주제를 한눈에 보여 주는 대표 썸네일 한 장을 둔다.
- 관련된 기존 브링이슈 글이 실제로 공개되어 있으면 본문 흐름에 맞춰 내부 링크를 연결한다.

### 5단계: 검증

브리프와 원고가 준비되면 검증 도구를 실행한다.

```powershell
python scripts/validate_brief.py <브리프.yaml>
python scripts/validate_draft.py <원고.md> --keyword "대표 키워드"
```

오류, 미해결 `확인 필요`, 사실 근거 부족, 사진 미검수 또는 개인정보 위험이 있으면 발행하지 않는다.

## 7. 발행 직전 강제 검수

발행 버튼을 누르기 직전에 현재 저장된 브링이슈 매뉴얼과 템플릿을 다시 읽는다. 과거에 읽었다는 기억이나 이전 검수 결과로 대신하지 않는다.

필수 확인 항목:

1. 제목의 약속을 본문에서 해결했는가
2. 최신 정보가 공식 출처 기준으로 확인됐는가
3. 대표 이미지와 본문 이미지가 잘리지 않고 읽히는가
4. 실제 화면과 설명용 디자인을 혼동하지 않았는가
5. 긴 문장을 나누고 의미 묶음 사이에 실제 빈 문단이 보이는가
6. 번호 소제목과 본문 사이에 충분한 여백이 있는가
7. 문자 구분선이 아니라 실제 인용구·구분선·표 기능을 사용했는가
8. 가운데 정렬된 본문이 불규칙하게 좌우로 흩어지지 않았는가
9. 같은 사진, 문장, 체크박스와 상담 배너가 중복되지 않았는가
10. 내부 검수 문구, 출처 덤프와 불필요한 확인 기준일 문장이 본문에 남지 않았는가
11. 개인정보와 저작권 위험을 확인했는가
12. 전체공개, 검색허용, 카테고리와 예약 시각이 맞는가

한 항목이라도 불일치하면 먼저 수정하고 다시 미리보기로 확인한다.

## 8. 네이버 발행 절차

1. 요청된 네이버 계정이 맞는지 확인한다.
2. 원고와 이미지 순서를 대조한다.
3. 네이버 편집기에서 실제 서식, 구분선, 인용구, 표, 링크와 스티커를 적용한다.
4. PC와 모바일 미리보기에서 잘림, 문단 간격과 정렬을 확인한다.
5. 사용자가 승인한 공개 방식과 시각을 확인한다.
6. 즉시발행 또는 예약발행한다.
7. 발행 결과 페이지를 다시 열어 공개 여부, 제목, 이미지, 링크와 URL을 확인한다.
8. 실제 `logNo`와 공개 URL을 기록한다.

동일한 게시 작업 묶음은 사용자가 한 번 승인하면 글마다 반복 승인을 요구하지 않는다. 다만 게시 범위, 공개 상태, 예약 시각 또는 외부 전송 대상이 달라지면 다시 확인한다.

## 9. 텔레그램 공개 알림

브링이슈의 새 글이 실제로 전체공개된 뒤에만 등록된 텔레그램 채팅으로 제목과 공개 URL을 보낸다.

```powershell
python -m automation.bringcare_telegram.cli published --post-id <logNo> --title "글 제목" --url "공개 URL"
```

- 네이버 게시물 번호 `logNo`를 `post-id`로 사용한다.
- `telegram-state`에 이미 전송된 게시물은 다시 보내지 않는다.
- 예약 상태, 비공개 글과 공개 URL이 확인되지 않은 글은 보내지 않는다.
- 오류 보고에는 원인만 적고 토큰이나 Chat ID를 출력하지 않는다.
- 로컬 설정, 토큰, Chat ID와 전송 상태 파일은 Git에 넣지 않는다.

자세한 설치·명령은 `automation/bringcare_telegram/README.md`를 참고한다.

## 10. 발행 후 운영

발행된 글은 다음 시점의 성과를 `blog/automation/performance-ledger.csv`에 기록한다.

| 시점 | 확인 내용 |
| --- | --- |
| 72시간 | 초기 조회, 유입 경로, 제목·대표 이미지 반응 |
| 7일 | 검색어, 연령·성별, 검색·일반서비스 유입 |

확인할 수 없는 값은 0으로 추정하지 않고 `NA`로 기록한다. 일반서비스 유입을 전부 홈피드 유입으로 단정하지 않는다.

## 11. 보안·저작권·품질 금지사항

- 비밀번호, 쿠키, 인증 코드, API 토큰, 텔레그램 토큰과 Chat ID를 저장하거나 출력하지 않는다.
- 유튜브 원본 영상과 불필요한 대용량 중간 파일을 Git에 넣지 않는다.
- 타인의 영상·블로그 문장과 이미지를 그대로 복제하지 않는다.
- 참고 블로그의 구조와 읽기 방식은 참고할 수 있지만 문장과 고유 디자인은 복제하지 않는다.
- 공식 사이트 화면은 독자가 이해하는 데 필요한 범위로 캡처하고 출처를 관리한다.
- 검색·홈피드 노출, 조회수와 수익을 보장하지 않는다.
- 의료, 법률, 금융 정보는 개인별 진단·판단을 대신한다고 표현하지 않는다.

## 12. 후임자 첫날 체크리스트

1. 회사 저장소에서 `codex/bringissue-content-archive` 브랜치를 확인한다.
2. 이 문서와 `README.md`, 최신 콘텐츠 운영 매뉴얼과 템플릿을 읽는다.
3. 비밀 설정 파일이 저장소에 없는지 확인한다.
4. 네이버에서 `rancemo858` 로그인 상태와 브링이슈 블로그 권한을 확인한다.
5. 네이버 예약 목록과 최근 공개 글을 직접 확인한다.
6. `alerts.md`, 성과 원장, 주제 중복 원장과 발행 계획을 확인한다.
7. 파일상의 계획과 실제 네이버 상태가 다르면 실제 상태를 기준으로 원장을 갱신한다.
8. 미발행 원고 하나를 골라 공식 출처와 모든 이미지를 다시 검수한다.
9. 모바일 미리보기까지 통과한 뒤 사용자 승인 범위 안에서 발행한다.
10. 공개 URL과 `logNo`를 확인하고 텔레그램 중복 여부를 점검한다.

## 13. 장애 대응

### 로그인 만료·본인 인증·CAPTCHA

발행을 중단한다. 사용자가 해당 계정에서 로그인이나 본인 인증을 완료한 뒤 계정을 다시 확인하고 재개한다.

### 네이버 편집기 변경

기존 좌표나 기억으로 클릭하지 않는다. 현재 화면의 버튼과 미리보기를 다시 확인한다. 서식이 틀어졌으면 발행하지 않는다.

### 공식 자료 확인 불가

추측하지 않는다. 검증된 범위로 주제를 좁히거나 `검증대기`로 남긴다.

### 텔레그램 오류

토큰과 Chat ID를 노출하지 않고 인증, 네트워크, 중복 또는 설정 오류 중 원인만 보고한다. 네이버 발행 성공 여부와 텔레그램 알림 성공 여부를 따로 기록한다.

## 15. 인수인계 완료 기준

후임자가 다음을 혼자 수행할 수 있으면 인수인계가 완료된 것으로 본다.

- 올바른 네이버 계정을 구분한다.
- 성과와 중복 원장을 읽고 주제를 고른다.
- 공식 출처와 실제 이미지를 확인해 브리프와 원고를 만든다.
- 확정된 네이버 서식으로 모바일 가독성을 검수한다.
- 발행 직전 매뉴얼을 다시 읽고 불일치를 수정한다.
- 예약·공개 결과와 `logNo`를 확인한다.
- 중복 없이 텔레그램 공개 알림을 보낸다.
- 성과와 장애를 원장에 남긴다.
